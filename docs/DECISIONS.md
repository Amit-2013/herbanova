# Decisions and assumptions — HR upgrade and verification

This file records decisions that could not be settled from the code alone, so a later
reader can see why the implementation looks the way it does. The dashboard work kept its
log in `docs/DASHBOARD_DECISIONS.md`; this file starts with the whole-project audit and the
HR upgrade.

| # | Date | Decision / assumption | Why | Reversible? |
|---|---|---|---|---|
| D-01 | 1 Nov 2026 | `docs/DECISIONS.md` is created as the running log; `docs/DASHBOARD_DECISIONS.md` is left in place as the dashboard-specific history. | The brief names `docs/DECISIONS.md`, which did not exist. Deleting or rewriting the dashboard log would lose history. | Yes |
| D-02 | 1 Nov 2026 | "MD" is implemented as the Administrator plus any custom role the Administrator grants `hr:confidential`. No new `md` role is invented. | The live `roles` table has no MD role. Creating one would change access without authorisation. | Yes, by adding an MD role later |
| D-03 | 1 Nov 2026 | Confidential employee fields (bank name/account/IFSC, PAN, UAN, ESI) are returned masked to callers without `hr:confidential`, except the employee viewing themself and the Administrator. The response keeps the field present, with a masked display value and a `confidential` flag. | Removing fields would break existing screens; masking is additive and server-enforced. | Yes |
| D-04 | 1 Nov 2026 | Salary structure writes require `hr:confidential` or `hr:payroll_prepare` in addition to `hr:write`. | `hr:confidential` is described as the salary gate but did not gate writes; the change makes the key meaningful. The Administrator bypasses it. | Yes |
| D-05 | 1 Nov 2026 | `hr_payroll` approvals are visible only to users with payroll prepare/approve or confidential rights; other HR approvers keep their own categories. | Net payroll is confidential financial data and must not reach a leave approver. | Yes |
| D-06 | 1 Nov 2026 | Leave days are counted as **working days** (shift weekly offs and applicable holidays excluded) for new applications; historical stored `days` values are not recalculated. | D-07 | 1 Nov 2026 | Attendance and payroll period locks are additive, default unlocked, and every override needs an Administrator role, a written reason and an audit entry. | Existing periods must keep working; locks cannot silently change historical totals. | Yes |
| D-08 | 1 Nov 2026 | Statutory payroll (PF/ESI/PT/TDS) appears only where the Administrator has configured a component marked `statutory` with a rate. Unconfigured rules are shown as gaps; no rate is hard-coded. | "Do not invent rules." | Yes, by configuration |
| D-09 | 1 Nov 2026 | Notification e-mails use the existing test-mode mailer. A delivery is proven by the stored delivery/test record, never by sending to a real inbox. | Standing instruction: no real e-mail and no secrets printed. | Yes, when SMTP is approved |
| D-10 | 1 Nov 2026 | Bulk employee import accepts CSV only in this phase (Excel requires an extra parser). A template, preview with row errors, commit and undo are provided; imported rows are tagged with a batch id. | CSV is already used by exports; adding an Excel dependency is a larger change than the requirement needs. | Yes |
| D-11 | 1 Nov 2026 | The two employee endpoints (`/api/employees` and `/api/hr/employees`) are kept for compatibility. The HR endpoint becomes the authoritative read for the HR screens and gains the confidentiality rules; the legacy endpoint keeps its narrow public fields. | Existing screens and tests call both. Removing one would break them. | Yes, after callers migrate |
| D-12 | 1 Nov 2026 | "No data yet" is returned as an explicit availability flag/`null` rather than a fabricated zero where a figure has no source rows. Zero is shown only when the source was queried and is genuinely zero. | Never invent data or numbers. | Not applicable |
| D-13 | 1 Nov 2026 | A leave application counts working days, may not cross a calendar year, may not exceed a 90-day span, and a half-day application must be for a single date and a leave type that allows half days. | Balances are kept per year, and the other limits stop a typing error from creating an accidental year-long absence. | Yes, by editing the validators |
| D-14 | 1 Nov 2026 | Payroll treats a month with **no attendance rows** as fully present, a paid half-day as 0.5 present + 0.5 paid leave, an unpaid half-day as 0.5 present, and prorates earnings by payable days; incentive, overtime, bonus and reimbursement are not prorated. | This is the existing rule and the least surprising default for staff whose attendance was never recorded; inventing an absence would dock pay for a recording gap. The treatment is stated in the register rather than hidden. | Yes, but it would change historical totals |
| D-15 | 1 Nov 2026 | Salary components, structures and the payroll register require `hr:payroll_prepare`; `hr:confidential` alone reveals bank/ID values and payslips but not salary structures or the register. | Keeps an HR manager who is trusted with personal data but not payroll from reading pay. The Administrator can grant `hr:payroll_prepare` to any custom role. Verified live in `VERIFICATION_REPORT.md` §5. | Yes, by granting the key |
| D-16 | 1 Nov 2026 | The bank upload file needs **both** `hr:payroll_prepare` and `hr:confidential`, is available only for a processed or paid period, and its JSON preview masks account numbers. | The file contains full account numbers and net pay; two independent rights and a release check keep it to the payroll pair. | Yes |
| D-17 | 1 Nov 2026 | Payroll is not posted to the accounting ledger. The payroll register, payslips and bank file are the payroll record; no journal entries or payment vouchers are created. | There is no authorised salary-to-ledger mapping in the system, and inventing one would fabricate accounting entries. | Yes, once the mapping is approved |
| D-18 | 1 Nov 2026 | The scheduled HR e-mail pack carries headcount, attendance, leave, approvals and announcements but **no salary amount**. Department cost stays behind the confidential report in the application. | Pay must not travel in e-mail, including the test-mode pack; the pack can be forwarded beyond the payroll pair. | Yes, by an approved change |
| D-19 | 1 Nov 2026 | HR notifications are in-app; the digest e-mail uses the test-mode mailer only, runs once per recipient per day, and a delivery is proven by the stored record. | No real e-mail and no secrets until SMTP and recipients are approved. | Yes, when SMTP is approved |
| D-20 | 1 Nov 2026 | Letters, ID cards and leave statements apply the same server-side scope as the profile; the ID card omits bank, PAN, UAN, ESI and salary by design, and the leave statement is read-only (it does not create or adjust balances). | Outputs must not become a side channel around the screen's scope or an accidental write path. | Yes |
| D-21 | 1 Nov 2026 | The HR directory CSV export requires `hr:read` (not `report:export`) and masks confidential columns for the viewer. | Requiring the export key would remove export from the HR manager, who needs it for the directory. The limitation is documented instead of silently changing access. | Yes, if the roles are adjusted first |
| D-22 | 1 Nov 2026 | Every HR report needs `hr:reports`; the department salary-cost report additionally needs `hr:confidential` or `hr:payroll_prepare`. | `hr:reports` covers non-confidential HR reporting; salary cost is pay data and keeps the stronger gate. | Yes |
| D-23 | 1 Nov 2026 | `hr:attendance_self` alone may read the leave policy, own balances, own applications, own OD, letter templates and own outputs; row scope keeps those reads to the person (or their team for a manager). | Staff need self-service without being given `hr:read`; the handler scopes every read, so the extra read surface does not expose a colleague's record. | Yes |
| D-24 | 1 Nov 2026 | Statutory components map to four fixed heads — `pf`, `esi`, `pt`, `tds` — and contribute to a head only when an active component is marked `statutory` with that head and a rate. An unconfigured head is reported as a gap. | Fixed heads keep the statutory summary and reconciliation stable; "do not invent rules" forbids hard-coded rates. | Yes, by configuration |
| D-25 | 1 Nov 2026 | SMTP settings are saved in a single `email_settings` row (id 1), managed on Settings → Email and SMTP. The environment remains the deployment default for every field; a saved value wins and an empty saved field falls through. No seed row is created. | The owner must be able to configure SMTP without editing the environment, while an installation that never opens the screen must behave exactly as before. A missing row also means "use the environment", so no existing test or deployment changes. | Yes, by deleting the row |
| D-26 | 1 Nov 2026 | The saved SMTP password is encrypted with Fernet keyed from `APP_SECRET`, never returned, and audited only as unchanged/replaced/cleared. Live mode needs both the saved mode and `EMAIL_MODE=live`; the API refuses to save `live` while the environment says `test`. | A browser session must not be sufficient to put the installation into production mail mode, and a database copy must not reveal the password. | Yes, by rotating `APP_SECRET` (saved password becomes unreadable and must be re-entered) |
| D-27 | 1 Nov 2026 | The test composer always prefixes `[TEST]`, defaults to a dry run that opens no socket, and records every attempt in `email_test_messages` with mode `dry_run` or `smtp`. The message types are `test`, `hr_notice`, `report_notice` and `custom` with editable defaults. | Satisfies "start sending test emails" without any route to a real inbox by accident; the stored row is the evidence of what was rendered and whether it reached a server. | Yes, by an approved live-mode change |
| D-28 | 1 Nov 2026 | Roles, the permission tree, feature switches and the access-control summary live on a dedicated **Roles & Permissions** screen (`#/roles`, sidebar under People and admin). Logins and the employee master stay on a separate **Logins and employees** screen reached from Settings; the two screens are not merged. | The brief names Roles & Permissions as the place for every permission and On/Off control; keeping user accounts on the same page mixed two different jobs and buried the switches. Splitting is additive and every old link still resolves. | Yes, by merging the screens again |
| D-29 | 1 Nov 2026 | A feature switch is enforced per request; it is not a bulk edit of `roles.permissions`. Switching a module off refuses its API prefixes and removes its keys from the **effective** set that `/api/auth/me`, the navigation and the Overview see. Switching it back on restores exactly what each role stored. | Rewriting stored role sets would destroy the Administrator's configuration and make the switch irreversible without a backup. The effective-set approach is reversible and audited (`feature.update`). | Not applicable |
| D-30 | 1 Nov 2026 | The Overview module list is read-only status. The only On/Off controls are on Roles & Permissions, and only the Administrator role can call `/api/features`. | The brief moves the controls out of Overview; leaving a second control path would create two sources of truth for availability. | Yes, by an approved change |
| D-31 | 1 Nov 2026 | Customers and Distributors are one screen at `#/customers`, titled **Customers and distributors**. The two tables were reading the same rows from `state.dists`; the merged table keeps the customer search plus the distributor status filter, credit figures and meter, and one action set (`Open`, `New order`, `Change limit`) gated by `distributor:write`, `sales:write` and `credit:manage`. `#/distributors` is kept as an alias in `route()`. | Two lists of one master meant two places to fix every column and two different permission behaviours; the old Customers page also offered actions its readers could not complete. The alias keeps dashboard drill-downs, bookmarks and links working, so nothing existing breaks. | Yes, by restoring the second view |
| D-32 | 1 Nov 2026 | Attendance requirements are configured as rules that may target any mix of branch, office, designation and employee, with optional effective dates, priority, shift and attendance-mode overrides. Resolution is by specificity — employee (1000), office (100), designation (10), branch (1) — then priority, then the newest rule; with no matching rule, attendance is required. A day the policy exempts is **not required**, never a gap and never an inferred absence, in the monthly register and in payroll. Manual, bulk, correction and self check-in are refused with the rule's source in the message. An employee belongs to one office, and that office belongs to one branch; the branch is inferred from the office and a mismatched pair is refused. `hr_admin_id` on a branch or office names the person responsible for HR there; it is not an approval or data-scope override. | The brief asks for attendance that can be required per branch, office, work location and person, and for tracking only when required. A single most-specific rule keeps the behaviour explainable on screen, and refusing writes for exempt employees prevents a manual entry from contradicting the policy. The responsible-person field is informational so naming it cannot silently widen anyone's access. | Yes, by editing or deleting rules; migration `0018_attendance_rules` has a rollback |

| D-33 | 3 Nov 2026 | Product **category**, **brand** and **reorder level** are optional free-text/numeric fields (migration `0024`). A blank category groups as **Uncategorised**; a blank reorder level is **not set** and is excluded from the low-stock rule, never treated as zero. Categories and brands are suggested from values already saved, not from a fixed taxonomy. | A fixed list would need an owner-approved taxonomy before any product could be created, and inferring a category or a level from the product name would fabricate data. Free text keeps capture possible today; the cost (two spellings of one category) is documented. | Yes, by adding a managed category master |
| D-34 | 3 Nov 2026 | A sales order stores the date **promised to the buyer** (`expected_delivery_date`) and the moment it became **approved** (`approved_at`). The promise is optional and cannot be in the past; it may be set or cleared until the order is closed, and every change is audited. Lateness compares the IST dispatch date with the promise. Orders without a stamp or a promise are excluded from the respective averages rather than counted as zero. | Separating approval from dispatch is the only way to report approval time honestly; imputing a stamp for historical orders would invent a measurement. An absent promise must not become an on-time delivery. | Yes, by an approved change |
| D-35 | 3 Nov 2026 | "Sales by category" uses the product's **current** category for every historical invoice; the panel states the figure is as printed on issued invoices and names uncategorised revenue separately. | Invoice lines do not freeze the category at issue time, and adding a frozen copy now would either invent history or require a risky backfill. Correcting a product's category intentionally re-groups its history, which is what a mis-categorised master needs. | Yes, by freezing category on invoice lines in a future migration |
| D-36 | 3 Nov 2026 | A payroll month the reporting window cuts short contributes its **approved gross allocated by each employee's working-day share** and is returned as `prorated` with the `allocated` amount; a month with no approved payroll is **excluded** and named in GAP-P03. **Total expenses** and **Payroll (gross)** therefore show a provable partial total marked `Partial` with a "Fix this" link to `#/hr/payroll`. **Net profit** stays `No data yet` until every input for the window is complete. A payroll run also lists the active employees it skips and the reason, and records them on the audit entry. | The brief names these figures as "No data yet" gaps, but only a genuinely missing input may be absent. Allocating an approved month by working days is arithmetic on recorded amounts, not an estimate; a month with no approved payroll cannot be allocated at all, so it stays a gap rather than becoming zero. Net profit is a residual, so a partial component would make it wrong rather than partial. Listing skipped employees closes M-06 without changing who is paid. | Yes, by changing the allocation rule or requiring a full-month window for all three figures |
| D-37 | 3 Nov 2026 | A **financial year** (1 April to 31 March, label `2025-26`) can be closed once its last day has passed and once at least one document exists, with a reason of five characters or more. Closing does not write entries: it refuses every dated document in that year with HTTP 423 — dispatch and invoice, receipts and payments, credit/debit notes, invoice cancellation, expenses, cost corrections/backfill and free-sample notes. Only the Administrator reopens it, with a reason; close and reopen are audited on `financial_year:{label}`. The monthly accounting lock remains and is checked first. | A year-end journal the system writes would have to be invented. (Since D-43 a person can post a closing voucher by hand; the close itself still writes none.) Freezing the dated documents in a finished year gives the same protection against silent restatement, stays reversible, and cannot block current trading because only completed years may be closed. Administrator-only reopen keeps one person from quietly rewriting a closed year. | Yes, by reopening the year and deleting the close row; migration `0025_due_dates_and_year_close` rolls back |
| D-38 | 3 Nov 2026 | An issued invoice **freezes** the distributor's `payment_terms_days` and computes `due_date = invoice_date + terms`. A distributor with no terms stores NULL; the invoice then reports "no due date" and ageing counts it in `no_due_date` rather than assuming a term. A later change to the master cannot move an issued invoice. Supplier payables keep using current terms and say so. | The buyer holds the invoice, so its due date must not change when a master is edited. A guessed term would fabricate an overdue figure; an explicit `no_due_date` bucket makes the missing input visible. Supplier terms are a separate estimation because supplier bills are not captured with terms. | Yes, by adding supplier-bill terms and changing the estimate |
| D-39 | 3 Nov 2026 | Input tax comes **only from a captured supplier bill** (`purchase_invoices`), never from a purchase order. A bill records the tax head by head; a bill without tax captured contributes no ITC. Capturing or reversing a bill does **not** change payables, which stay goods received minus payments. | A purchase order carries an agreed cost, not a tax invoice; splitting tax on a PO would invent a document that does not exist. Keeping payables on the receipt basis means adding the register cannot silently restate what is owed. | Yes, by capturing supplier invoices as the payable document |
| D-40 | 3 Nov 2026 | ITC eligibility is **recorded, not judged**: the person capturing the bill sets `itc_eligible`, and the application never decides whether a credit is blocked. Blocked input is totalled and displayed but never netted. Creditable GST on expenses stays a **memo** (`included_in_net: false`) because an expense stores one GST amount with no CGST/SGST/IGST split. | Blocking rules depend on facts outside the application (use, amendments, portal status). Guessing them would change the payable. Putting a single expense amount into a head column would misstate every head, so a memo is the only honest presentation until expenses capture a split. | Yes, by adding a head split to expenses or an eligibility engine |
| D-41 | 3 Nov 2026 | The figures **reported as filed** on GSTR-1 and GSTR-3B are captured by hand per month and compared with the computed register. A difference is shown with both figures and is never auto-corrected or resolved. The application does not file and does not read the portal. | Only the practitioner knows what was actually filed, including amendments and portal-side adjustments the book does not contain. Recording the reported figure turns reconciliation into a visible comparison instead of a claim of compliance. | Yes, by adding a portal integration with owner approval |
| D-42 | 3 Nov 2026 | Statutory dues read **vendor TDS** from posted supplier bills and **payroll PF/ESI/PT/TDS** only from periods that reached `approved`, `processed` or `paid`. A draft payroll is not a liability. Challans are recorded deposits and are applied cumulatively per head, not matched to individual deductions; outstanding is the remainder. A head with no source is `available: false` with a reason, never zero. | A draft run can still change, so treating it as withheld would overstate the liability. Matching each challan to a deduction would invent an allocation the deposit record does not contain, so the cumulative remainder is the only defensible figure. | Yes, by adding a challan-to-deduction allocation |
| D-43 | 3 Nov 2026 | The stored ledger is **manual and additive**: documents are not posted as vouchers, and a voucher is a person's own double-entry entry. A draft may be unbalanced and is not in the books; posting requires debit to equal credit; a posted voucher is corrected only by a mirror voucher dated **today**, never back-dated into a month that may already be locked. The balance sheet merges openings, posted vouchers and the document trial balance **by head and role**, keeps the three layers in separate columns, and names in warnings what the document layer does not cover (expenses, payroll, stock cost, fixed assets) rather than guessing it. | Auto-posting documents would make every existing report change meaning and would require a posting rule for each document type that the owner has not approved. A mirror dated today keeps the correction possible when the original month is locked and leaves an unbroken trail. Separate columns let a reader see which layer a balance came from; a single merged figure would hide a partial document layer. | Yes, by adding a document-to-voucher posting rule or changing the reversal date rule |
| D-44 | 3 Nov 2026 | The frontend and backend run as **two processes**: `scripts/run_backend.py` (uvicorn, database, cookies, permissions, every `/api` route) and `scripts/run_frontend.py` (standard-library static server for `static/`, proxying `/api`, `/docs`, `/openapi.json` and `/redoc`). The browser keeps one origin, so the session cookie is first-party and the JavaScript keeps its relative URLs. The frontend is a development/LAN server, not a production web server; production puts TLS and a real reverse proxy in front of it. | Splitting the processes was requested so the API can run, restart and scale independently of the UI; proxying rather than cross-origin calls avoids weakening the cookie (`SameSite`, `Secure`) or adding CORS. Keeping the frontend on the standard library means no extra dependency for a server that only copies files and forwards a path. | Yes, by replacing the frontend server with a production proxy or serving both from one process |
| D-45 | 3 Nov 2026 | Every Accounts KPI card carries its **own** destination, built by the server (`accounting.report()["cards"][].href`), with the dashboard window appended (`?from`/`?to`, and `?as_of` for ageing). A card opens the report that proves it; cards that share a report (Revenue and Output GST, Collections and Cash and bank) still open it with the same window, and Over 60 days and Payables-within-7-days open with their own filter. A card with no data links to the section that explains its gap. | One shared destination would make a tile look like a link while hiding where its figure came from. Building the address on the server keeps the card and the report on one window, so they cannot disagree. Changing a destination is a one-line server change rather than a browser edit. | Yes, by changing the `href` for a card |
| D-46 | 3 Nov 2026 | The Administrator second factor is **TOTP only** (RFC 6238, 6 digits, 30 seconds, ±1 step) and is enforced by the **backend**, not by an OTP screen. `admin` and `super_admin` get no session from the password step; the secret is sealed with a key derived from `APP_SECRET`; a used time step cannot be replayed; 10 argon2 recovery codes are single-use; five wrong codes pause entry for 15 minutes; the session carries an `otp` claim that `current_user` requires for an enrolled account. Every other role keeps password-only sign-in. | The brief requires the second factor for the Administrator roles only, with no SMS, e-mail or internet on the phone. Server enforcement is the only way a screen cannot be bypassed by calling the API directly. TOTP over a sealed shared secret avoids a paid SMS provider and works offline. Requiring the `otp` claim means even a mistaken password-only cookie is refused. | Yes, by adding WebAuthn or changing the role list |
| D-47 | 3 Nov 2026 | SMTP **transport is decided by the port**: 465 means implicit TLS and 587 means STARTTLS, even when the saved "Connection security" says otherwise; any other port uses the saved choice. The settings screen reports the transport in use. | A saved setting that contradicts a well-known port is the usual cause of "the password is correct but sign-in fails": the client speaks plaintext to an implicit-TLS port or STARTTLS to a plaintext one. Letting the port win removes a silent misconfiguration while leaving unusual ports fully configurable. | Yes, by changing `_transport` in `app/services/email_config.py` |
| D-48 | 3 Nov 2026 | A **database error during delivery** rolls the session back and the worker **re-reads** the delivery before recording the failure; a failed settings read also rolls back; a schedule with no `next_run_at` is committed even when nothing is due. The connection pool is bounded (10 + 20 overflow, 30 s wait) and recycled every 30 minutes. | Without the rollback the session stays in a failed transaction, so recording the failure raises `PendingRollbackError`, the delivery remains "sending" until a sweep, and the next read fails too. Without the pool bound one idle worker can exhaust PostgreSQL; without recycling a connection the network dropped while idle fails the first statement after it. These are correctness fixes, not tuning. | Yes, by changing the pool or retry rules |
| D-49 | 3 Nov 2026 | A credit or debit note is opened from Billing in the shared drawer and printed through the **existing** secure-print path (`POST /api/print/{kind}/{id}`), not through a new document builder. Open shows the stored note and its print-log verification; Print is shown only with `print:document`. | The document builder already renders both note kinds and records a hash, print log and verification page, so a second path would duplicate a security-sensitive flow and could drift from it. Reusing it means a note print is as verifiable as an invoice print. | Yes, by adding a separate note template |

## Open decisions for the product owner

These do not block the build; the implementation proceeds with the stated default and the
default is visible in the UI.

| # | Question | Default used |
|---|---|---|
| Q-01 | Which custom roles besides Administrator should hold `hr:confidential`? | Whatever the live role table grants; no role is changed automatically. |
| Q-02 | Is leave encashment a payroll earning? | Not paid automatically; a recorded encashment creates an audit entry and a note, and payroll uses only configured components. |
| Q-03 | Should attendance lock also block corrections? | Yes: any change to a locked month needs the Administrator override and reason. |
| Q-04 | Is an MD login required separately from the Administrator? | No MD role is assumed; the Administrator acts for the MD until an MD role exists. |
| Q-05 | Should the HR manager see salary structures without `hr:payroll_prepare`? | No. `hr:confidential` covers bank/ID and payslips; salary structures and the register stay with payroll. Grant `hr:payroll_prepare` if the answer changes. |
| Q-06 | Should the HR directory export require `report:export`? | No, because it would remove export from the HR manager. The CSV is masked per viewer; revisit together with the role sets. |
